本技能用于创建具有明确审美主张、可用于生产的前端界面。目标不是堆砌装饰，而是用清晰的设计判断、扎实的实现和细节控制，让界面看起来像为当前场景专门设计过。

用户可能会要求你构建组件、页面、应用、海报式网页、仪表盘、React/Vue 组件、HTML/CSS 布局，或对现有 Web UI 进行美化、重构和风格升级。你需要在实现可工作的代码时，同步承担设计师的判断职责。

## 设计思考

开始编码前，先理解场景，并主动选择一个鲜明但合理的视觉方向：

- **目的**：这个界面解决什么问题？谁会使用？用户最需要看到、理解或完成什么？
- **语气**：选择明确的审美方向，例如极简克制、复古未来、自然有机、奢华精致、玩具感、杂志编辑、粗野主义、几何装饰、柔和粉彩、工业工具感等。方向可以大胆，但必须服务场景。
- **约束**：确认技术栈、性能、响应式、可访问性、已有设计系统和业务限制。
- **记忆点**：这个界面最值得被记住的视觉或交互特征是什么？只选一两个核心亮点，并执行到位。

**关键原则**：先确定概念，再精确执行。强烈的极繁主义可以成立，克制的极简主义也可以成立；真正重要的是意图清晰，而不是视觉强度本身。

最终交付的代码应当：

- 功能完整，能够真实运行；
- 视觉上有辨识度，不像模板；
- 风格统一，有明确审美立场；
- 在字体、间距、颜色、动效、层级和细节上经过打磨；
- 在现有项目中工作时，尊重已有产品语境和设计系统，不做突兀改造。

## 前端审美准则

### 字体

选择能强化气质的字体。避免默认依赖 Arial、Inter、Roboto、system 等普通字体栈，除非项目设计系统已经明确规定。可以用有个性的标题字体搭配易读的正文字体，让文字本身参与塑造风格。

### 色彩与主题

使用 CSS 变量管理颜色、阴影、边框和背景。色彩应当有主次：一个明确的主色或基调，加上少量锐利的强调色，通常比平均分配的安全配色更有效。避免默认的"白底紫色渐变"式 AI 套路。

### 动效

动效要服务节奏和反馈。优先使用 CSS 动画完成 HTML/CSS 场景；React 项目中如果已有 Motion 等库，可以沿用。一个设计良好的入场动画、分层延迟和关键 hover 状态，通常比到处散落的微动效更有价值。

### 空间与构图

不要默认使用居中卡片、等距网格和常规 SaaS 布局。可以考虑非对称构图、重叠元素、斜向动线、打破网格的装饰、充足留白或有控制的高密度信息排布。空间应该帮助用户理解内容层级。

### 背景与细节

背景不应只是纯色填充。根据审美方向加入合适的氛围和深度，例如渐变网格、细微噪点、几何纹理、半透明层、戏剧化阴影、装饰边框、光晕、纸张质感或颗粒覆盖。但所有细节都必须围绕同一个视觉概念。

## 避免通用 AI 审美

不要生成缺乏上下文的模板化界面。尤其避免：

- 过度使用 Inter、Roboto、Arial、系统字体；
- 紫色渐变加白色卡片的陈词滥调；
- 可预测的 hero 区、三列功能卡、圆角玻璃拟态组件；
- 没有业务特征的图标堆砌；
- 所有项目都长得相似的安全设计；
- 为了显得"高级"而加入无意义的模糊、发光和阴影。

每次设计都应根据当前产品、受众、内容和情绪重新判断。不要在不同任务中反复收敛到同一套字体、配色和布局。

## 实现要求

- 根据审美目标匹配实现复杂度。极繁设计需要更丰富的层次、动画和视觉系统；精致极简设计需要更严格的间距、比例、字体和留白控制。
- 优先写清晰、可维护、可运行的代码。视觉实验不能牺牲基本可用性。
- 保证响应式表现，至少考虑桌面和移动视口。
- 保持可访问性：足够的对比度、可聚焦状态、语义化结构和可读文字。
- 如果处于已有项目中，先阅读现有组件、样式变量和设计约定，再决定如何延展，而不是强行覆盖。
- 不要无端引入大型依赖；只有当项目已有相关库或需求明确时才使用。

## 静态文件后的自动预览

当本技能创建或修改可直接预览的静态前端文件时，例如 `index.html`、`.html`、`.css`、`.js`、`.svg` 或纯静态资源目录，完成文件写入后必须自动启动 Web 服务，除非用户明确要求不要启动。

启动规则：

- 优先使用项目已有的启动方式，例如 `package.json` 中的 `dev`、`start`、`preview` 脚本，或 `Makefile`、Compose、框架配置声明的命令。
- 如果只是纯静态文件且项目没有启动脚本，则自动选择一个当前可用端口，并在静态文件所在目录启动简单 HTTP 服务，例如 `python3 -m http.server <可用端口> --bind 0.0.0.0`。
- 使用 tmux 后台运行服务，不要在前台阻塞当前会话。
- 启动前检查是否已有可复用的 tmux session/window，避免重复启动同一个服务。
- 启动后读取日志或检测端口，并向用户提供可访问地址；如果存在 `WORKSPACE_PORT_URL_TEMPLATE`，用其中的 `{{.port}}` 生成公网 URL。
- 不要询问用户选择端口；从 8000 开始检测，自动使用第一个可用端口。如果首选端口被占用，继续尝试后续端口，并在启动后说明实际端口。
- 如果无法启动服务，明确说明原因，并给出需要用户补充的信息或命令。

记住：优秀的前端界面不是"更花"，而是"更准确"。大胆选择，克制执行，把每个视觉决定都落实到代码细节中；静态产物完成后，要让用户可以立即打开预览。
